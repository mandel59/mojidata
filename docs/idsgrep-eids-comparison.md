# IDSgrep and Mojidata search over the same EIDS corpus

## Result

On the eight queries in
`packages/mojidata-api-bench/benchmarks/idsgrep-eids-cases.json`, IDSgrep
0.6 and Mojidata returned identical identifier sets. This includes literal,
exact structural, single-use wildcard, fragment, and whole-tree queries.

Mojidata FTS5 was fastest in all eight warm-cache end-to-end measurements.
For fragment searches it was 4.4x to 83.4x faster than indexed IDSgrep.
The result is more mixed for whole-tree searches: indexed IDSgrep was faster
than Mojidata FTS4 and BV128 for the selective exact query, but FTS5 remained
2.5x to 2.7x faster.

These timings compare the available public IDSgrep command-line interface
with an in-process Mojidata search using a persistent SQLite connection.
IDSgrep timings therefore include process startup. IDSgrep's own CPU
statistics are recorded below to make that effect visible.

## Inputs

  archive SHA-256
  `2c07029bab12d9ceefddf447ce4213535b68d020b093a593190c2afa8a577c7c`.

  This is the CHISE snapshot bundled in the 2021 IDSgrep release, not current
  CHISE data.
- The EIDS adapter produced 156,721 IDSFlow records and skipped 6
  unrepresentable entries. No additional recursive decomposition was applied.
- IDSgrep's sibling bit-vector index was generated by the same IDSgrep binary:
  3,761,480 bytes, SHA-256
  `a6063e2d7f4ebbc06c6da86eb618640e24e0496989f472bc729f74cbf4a1cff6`.
- Mojidata databases generated from those records:

  | Backend | Bytes | SHA-256 |
  | --- | ---: | --- |
  | FTS4 | 16,699,392 | `bcb30527f526df000695232f63d36357e1b1ec8e94599b5d2433975b8adeaf28` |

## Comparable query fragment

Mojidata searches for a complete pattern tree anywhere in an IDS by default.
The corresponding IDSgrep query uses its unary match-anywhere operator:

```text
Mojidata:  ⿰？心
IDSgrep:   ...⿰?心
```

Mojidata's `§pattern§` whole-tree anchors correspond to an IDSgrep pattern
without `...`:

```text
Mojidata:  §⿰？心§
IDSgrep:   ⿰?心
```

The comparison is restricted to one complete Unicode IDS tree using ordinary
IDCs and literals. A Mojidata `？` or a variable used only once maps to
IDSgrep `?`. The following were excluded because IDSgrep 0.6 and Mojidata
do not give them the same meaning:

- repeated Mojidata variables and subtree equality;
- incomplete serialized fragments or patterns crossing tree boundaries;
- multiple alternatives or multiple query groups;
- EIDS-specific operators and encoded multi-code-point atoms.

IDSgrep results were parsed through the same EIDS converter used to build the
Mojidata corpus. This excludes the same six unrepresentable input entries
from both sides and compares unique root identifiers rather than raw lines.

## Performance

Measurements used 5 warm-up runs followed by 30 measured runs in a
deterministically shuffled order. Values below are median wall-clock
milliseconds. IDSgrep scan uses `-I`; IDSgrep indexed uses the generated
sibling `.bvec` file.

| Case | IDSgrep indexed | IDSgrep scan | Mojidata FTS4 | Mojidata FTS5 | Mojidata BV128 |
| --- | ---: | ---: | ---: | ---: | ---: |
| fragment literal `木` | 143.37 | 149.94 | 32.90 | 32.86 | 58.54 |
| fragment exact `⿰火土` | 144.21 | 153.64 | 3.61 | 1.73 | 20.71 |
| fragment exact `⿱日月` | 130.23 | 154.44 | 3.97 | 2.58 | 22.44 |
| fragment wildcard `⿰？心` | 142.09 | 151.93 | 15.38 | 13.41 | 53.43 |
| fragment wildcard `⿱木？` | 131.36 | 155.20 | 6.14 | 4.35 | 40.63 |
| fragment nested `⿱木⿰木木` | 130.15 | 153.74 | 7.96 | 4.02 | 26.86 |
| whole-tree exact `§⿰火土§` | 10.11 | 112.03 | 12.83 | 3.73 | 13.50 |
| whole-tree wildcard `§⿰？心§` | 27.64 | 112.85 | 25.32 | 11.09 | 15.05 |

The indexed IDSgrep p95 values ranged from 11.67 ms for whole-tree exact
search to 149.98 ms for the fragment wildcard-heart query.

IDSgrep's index is highly effective for root matching: it reduced median
time by 11.1x for `⿰火土` and 4.1x for `⿰?心`. It helps much less with
`...` queries (1.05x to 1.19x). Its internal statistics explain the
difference:

| IDSgrep query class | Exact tree checks | Reported user CPU |
| --- | ---: | ---: |
| fragment `...⿰火土` | 142,929 | 145.9 ms |
| fragment `...⿰?心` | 144,324 | 146.1 ms |
| whole-tree `⿰火土` | 751 | below timer resolution |
| whole-tree `⿰?心` | 18,987 | 18.0 ms |

The original index filters root patterns well, but match-anywhere patterns
still send most of the 156,727 parsed EIDS trees to exact checking. Mojidata's
inverted indexes are much more effective for the tested fragment searches.

FTS5 is the best Mojidata backend in this workload. BV128 is smaller on disk,
but its broad Bloom-vector candidate sets and exact verification make it
slower than FTS4/FTS5 for all six fragment cases.

## Caveats

- These are warm-cache measurements on WSL2, Linux
  `6.18.35.2-microsoft-standard-WSL2`, AMD Ryzen 7 3700X, Node.js v24.17.0.
- IDSgrep process startup is included. The near-zero IDSgrep user CPU for the
  selective root query shows that its core indexed lookup is faster than the
  10.11 ms CLI wall time suggests.
- Mojidata used an in-process persistent database connection. A Node CLI
  startup benchmark would answer a different deployment question.
- During timing, IDSgrep still formatted full matching EIDS entries and wrote
  them to a discarded stream; Mojidata materialized identifier arrays.
- The build lacked IDSgrep's optional BDD dependency. Results may differ in a
  build with that layer.
- Only one historical CHISE snapshot and eight deliberately comparable
  queries were tested.

## Reproduction

The reusable runner is
`packages/mojidata-api-bench/benchmarks/compare-idsgrep-eids.ts`; its query
manifest is `idsgrep-eids-cases.json`.

```sh
yarn workspace @mandel59/mojidata-api-bench bench:idsgrep-eids -- \
  --idsgrep /path/to/idsgrep-0.6/idsgrep \
  --eids /path/to/idsgrep-0.6/chise.eids \
  --fts4 /path/to/fts4/idsfind.db \
  --fts5 /path/to/fts5/idsfind.db \
  --bvec /path/to/bvec/idsfind.db \
  --iterations 30 \
  --warmup 5 \
  --output /path/to/result.json
```

The final raw result JSON had SHA-256
`2bd0b9ce8b4b40f6cf7c2f934dc33e49f075216d0c21758643c113ec62bb45d3`.
